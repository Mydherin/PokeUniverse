## Playing a Milestone

Same steps as Phase 6 and 7 (build, play the milestone's **Manual Test**, regression check, fix, cut the file down; setup in [How to Test in Game](../../README.md#how-to-test-in-game)). Differences:

- **Other players are bots** (M1 on): `node infra/bots/bots.ts --count N --map <id>` beside the real player in the browser pane. A second real player, if needed, is a second browser tab after the bots exist: one Google account can only play one copy (take-over), so the second tab logs in a bot by token (M1's `?bot=` dev login, D16).
- **Regression check** adds, from M2 on: the real player walks both maps and the stairs with 5 bots around; a wild battle in the test grass and the room trainer still work; no `Correction` while walking through bots (D6).
- Bots' accounts are dev data: `make bots-clean` (M1) removes them; nothing they leave is committed.

## Decisions

| # | Decision |
|---|---|
| D1 | **A zone is a map + phase** (D19): everyone in a zone gets every other player's events there, nothing from other zones. No viewport culling now; M8 adds it only if the measured budget (D18) needs it. |
| D2 | **Each replica runs its own zone per map** for its own connections (zone.go as now) and the zones of one zone key share their events over NATS `world.zone.<map>.<phase>`: each tick a zone publishes its local players' `ZoneEvents` (only when non-empty), and subscribes only while it has players there. *Why:* `mic-core` stays stateless (no zone ownership, no routing, any replica takes any player); NATS keeps one publisher's order, and a player's events always come from the replica that owns its session. |
| D3 | **Snapshot of the others from Redis:** `zone:<map>:<phase>` hash, trainer → encoded `OtherPlayer`, written in the zone's tick pipeline with the positions (saved before shown) and removed on leave, warp and disconnect, all in the same Lua session check as `live`. A player entering reads it once; deltas follow. Local players also come from memory, never twice. |
| D4 | **No map connections yet:** players across a map border (FireRed's connected maps drawn together) come with the maps that have them (Phase 12). Warps already change zone. |
| D5 | **Payloads (minimal, numeric):** `OtherPlayer{id, name, gender, x, y, facing, follower, in_battle}`; `id` is the trainer's account ID; `name` is sent once on join (chat needs it, D13), never per event. Deltas: `PlayerJoined{player}`, `PlayerLeft{id}`, `PlayerMoved{id, x, y, facing, run}` (the tile reached; the client animates from the last one), `PlayerTurned{id, facing}`, `PlayerFollower{id, follower}`, `PlayerBattle{id, in_battle}`, `ChatMessage{id, text}` (M5). |
| D6 | **Players don't block each other**, nor their followers: steps through another player are valid and predicted as now. *Why (MMO):* blocking doors, stairs and narrow paths is griefing, and a step can't be predicted against a player on another replica. FireRed's link players do collide (`LinkPlayerDetectCollision`, Cable Club only). Drawn by feet as any object event, so the one lower on screen is in front. |
| D7 | **One `ZoneEvents` per zone tick, encoded once:** the zone marshals the tick's events (local and those received over NATS since the last tick) once and every local player gets the same bytes, wrapped in its own envelope (the envelope's `seq` field plus the pre-encoded field 22). A client ignores events with its own `id`. The player's own answers (`Correction`, `Script`, …) stay as they are. |
| D8 | **Others' steps on the client:** a queue per player; each step plays FireRed's walk (16 frames) or run (8 frames) from the tile it stands on. With more than 2 queued it plays them at running speed; a step that isn't to a neighboring tile (a correction, a long gap) places them there. Turns change the frame at once (`PlayerTurned`). No prediction, no interpolation beyond the step. |
| D9 | **A player in a battle, a script or a menu** is drawn standing where they are, facing their way, with nothing over them: FireRed has no such sign. `in_battle` is kept in `OtherPlayer` for Phase 9's social menu (busy). |
| D10 | **Others' followers follow the same rules as one's own** ([Phase 6](../../phase-6-pokemon-party/phase-6-pokemon-party.md), `world/follower.go`): the server sends the follower (species, shiny, tile, facing, hidden) on join and `PlayerFollower` when the party's lead changes; the client steps it onto the tile its trainer left with the same `FollowerModel`. Hidden on join and after a warp until the trainer's next step (`FollowMon_HideUntilStep`). Closes O7. |
| D11 | **Drawn as FireRed's object events:** the trainer's walking and running sheets by gender (as the own player's: Red's or Leaf's), the tall-grass effect over their feet, the same elevation rule as the own player ([Movement](../../../tech-stack.md#movement)). No names over them (FireRed shows none; user 2026-11-10, Q3). Names show in chat (D13) and on the trainer card shown by pressing A facing another player ([Phase 9](../../phase-9-social.md)). |
| D12 | **Appear and leave at once:** FireRed's link players have no spawn animation (`SpawnLinkPlayerObjectEvent`). A player warping out vanishes from the old map; on the new one they appear on the warp's tile, follower hidden. |
| D13 | **Chat goes to the zone** the sender is on (its general chat; user 2026-11-10, Q1), through the zone like any event. Not saved, not replayed on enter or reconnect (FireRed's Union Room chat keeps nothing). A line shows `NAME: text`. Text: FireRed's charset only (the font has no other glyphs; the same check as the naming screen's, with the charmap's printable characters), trimmed, 1-64 characters (ours: Union Room chat's 15 is too short for a typed message). Friends, private and party chat are [Phase 9](../../phase-9-social.md). |
| D14 | **Moderation:** length, charset and rate (D17) only; every message is logged by `mic-core` (`slog`, trainer ID, map) for later moderation. A word filter, muting and reporting are [Phase 13](../../phase-13-polish-launch.md)'s (user 2026-11-10, Q2). |
| D15 | **PC chat** (user 2026-11-10, Q4): `T` opens the chat and focuses the input, `/` opens it with `/` typed (room for commands later), `Enter` sends, `Esc` closes; `Enter` stays START while chat is closed; game keys aren't read while the input has focus. The log is a panel beside the GBA screen when the window is wide, below it otherwise, scrolled with the wheel. *Why:* `Enter` is START (GBA buttons table); `T` and `/` are the usual MMO keys. |
| D16 | **Bots are dev only:** `POST /api/dev/bots` exists only when `BOTS_SECRET` is set (empty in `.env.example`, never set in production), checked from the `X-Bots-Secret` header; it creates or reuses accounts `bot-<n>` (no Google subject, roles `user` and `bot`), each with a trainer `BOT<n>` (FireRed charset, ≤7) on the given map at a walkable tile, and returns their access tokens. The SPA accepts `/play?bot=<token>` only in dev builds: `vite` dev, or an image built with `BOTS_SECRET` set (`VITE_BOT_LOGIN`). Bots are tokens only: `infra/bots` needs no install (Node's own `WebSocket`). |
| D17 | **Rate limits:** intents stay at 20/s, burst 40 (realtime.go). Chat: 1 message per 2 s, burst 4, per connection; the client applies the same rule to its input (FireRed has no refusal message, so nothing is said); messages over it are dropped. Tuned in M8. |
| D18 | **Load budget (target, measured in M8):** 200 players on one map; zone tick ≤ 10 ms p99; downstream ≤ 8 KB/s per client with 50 others moving; the client keeps 60 fps with 50 others drawn on a desktop and 30 on a phone. M8 writes what was measured into tech-stack.md. |
| D19 | **Zone key = map + phase** (user 2026-11-10): a map may list story flags that split it into phases (Saffron with Team Rocket vs cleared); players in different phases are in different zones and never see each other. A map listing none has one phase, `0`. Phase 8 keys everything by it from the start, with phase `0` everywhere: the zone goroutine's key (`ZoneKey{map, phase}`), the NATS subject (D2), the Redis hash (D3), the snapshot (`others` from the same key only). The player's phase is computed on enter and warp (always `0` until Phase 10 adds map phase flags and private scene phases). *Why:* maps that really change can't be shared, and keying by map alone now would mean redoing M2-M5's keys later. |
| D20 | **Shared map, personal layer** (user 2026-11-10; built in [Phase 10](../../phase-10-pallet-town.md)): inside one zone, each player's FireRed story flags (kept per player on the server) decide their personal layer: stationary/legendary encounters (one per player), item balls and hidden items, temporary NPCs, beaten trainers, Cut trees, boulders, tiles a map script changes by flag. The server checks a player's collisions against their own flags, the client filters map objects by its own. Seeing another player walk through what blocks you is accepted (as PokeMMO). Permanent NPCs are shared by the zone. Phase 8 sends nothing of it. |
| D21 | **Chat is mobile-first** (user 2026-11-10): played mostly on phones (Chrome on Android, Safari on iOS, PWA), so the phone layout is designed first and PC has its own (D15). Keyboard handling is [ui.md's one pattern](../../../ui.md#mobile-keyboard): `interactive-widget=resizes-visual`, `visualViewport`, the shell pinned to it. *Why:* the player must see the whole sentence, the recent lines and the game while typing. |
| D22 | **Phone, composing (portrait):** top to bottom: the GBA screen scaled to fit what's left (integer scale if it fits, it keeps running, others keep moving), the latest lines (as many as fit, newest at the bottom), the input bar right on top of the keyboard. Input: textarea growing 1→3 lines then scrolling, a counter from 54 of 64 characters (D13), `enterkeyhint="send"` (the keyboard's send key sends) plus a send button. Characters the FireRed font lacks (emoji, …) are dropped as typed with a short hint ("Not in the game's font"); the same check as the server's. Touch D-pad/A/B/Start hidden; the own player doesn't move. **Landscape:** only the input bar and the last 2-3 lines show over the dimmed game; normal again when the keyboard closes. *Why:* the keyboard takes most of a landscape screen. |
| D23 | **Phone, not composing:** a speech-bubble chat button on the touch layer (above the Start button in portrait, top of the right column in landscape: clear of D-pad/A/B/Start), with an unread badge; a ticker of the last 1-2 lines in the band between the GBA screen and the controls, fading 5 s after the last line. Tap the ticker or the button → the **chat sheet** opens over the controls with the log and focuses the input. Gestures: swipe down on the sheet or the system back gesture (a history entry, `popstate`) closes it; dismissing the keyboard keeps the sheet open (tap the input to type again); drag the log to scroll older lines; long-press a line or tap its name → that player's actions (D24). *Why:* the usual mobile chat gestures; the controls stay usable while chat is closed. |
| D24 | **Look and growth:** Union Room chat's style (`union_room_chat*`): the log drawn with the FireRed font at an integer scale, a color per player from `messages.pal` (own lines in the own color); the input is a native textarea styled with the pixel font (IME, autocorrect, the OS keyboard). The sheet and the PC panel have a channel chip row (Phase 8: only "Zone"; [Phase 9](../../phase-9-social.md) adds friend and party chats) and each line keeps its player's `id` for the line-actions menu, which Phase 9 fills (trainer card, add friend, invite to party); Phase 8 opens no menu. |

## Already Built (don't rebuild)

- **Zones** (`mic-core/internal/world/zone.go`): one goroutine per map per replica, `do`/`call` inbox, 50 ms tick only while it has players, saves dirty players to Redis in one pipeline then flushes each player's `p.out` (saved before shown); `syncFollower` on tick.
- **Realtime** (`internal/realtime/realtime.go`): per-player `rate.NewLimiter(20, 40)`, read limit `maxMessage`, envelopes in `realtime/v1/realtime.proto` (`ClientMessage` 2-37, `ServerMessage` 2-21).
- **Contracts** (`world/v1/world.proto`): `WorldSnapshot` (own player only), `Avatar{x, y, facing, gender, follower}`, `Follower{species, shiny, x, y, facing, hidden}`, `FollowerChanged`, `Warped{…, follower}`.
- **Follower:** server `world/follower.go` (memory only: `placeFollower`, `followStep`, `syncFollower`); client `world/follower.ts` (`FollowerModel`), `firered/follower-sprite.ts`, used in `firered/overworld.ts` (`place`, `followerChanged`).
- **Renderer:** `world/view.ts` `WorldView.addCharacter(sheet)` → `CharacterView` (position, frame, over tiles, visible).
- **Live state** (`internal/live`): `player:<id>:pos`, `player:<id>:session` (15 s TTL, renewed every 5 s), Lua scripts checking the session. **Take-over across replicas:** `internal/sessionbus`, NATS `world.sessions.taken`.
- **Infra:** nginx re-resolves `mic-core` (`spa-pokeuniverse/nginx/default.conf`), so Compose replicas are reached; NATS users in `infra/nats/nats.conf` (`mic-core` has no subject limits; `mic-battles` only `battles.>`). Own player's overworld sheets in `firered/manifest.ts` (`owRed`, …).
- **Maps:** `lib-maps/maps/pallet_town_players_house_1f.yaml`, `_2f.yaml`.
